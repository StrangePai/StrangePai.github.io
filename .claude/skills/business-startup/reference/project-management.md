## 核心概念：金字塔階層

就像「憲法 → 法律 → 條則」一樣，每個專案都需要嚴謹的階層：

```
目的 (Purpose)        ← 為什麼這個專案要存在？
  └─ 願景 (Vision)    ← 完成後的產品長什麼樣子？
      └─ 設計支柱 (Design Pillars) ← 怎麼達成願景？（依優先順序排列）
          └─ 系統 (Systems)        ← 哪些具體系統／功能支撐每根支柱？
              └─ 細節 (Details)    ← 實作細節
```

- **每個決策都要能往上追溯到階層**
- 衝突時，**上位優先**勝出
- 團隊必須在開發前先對齊這個階層
- 定期檢視階層是否仍然成立

## 早期驗證（最重要）

**沒驗證過的東西絕不直接蓋下去：**

1. **概念驗證（POC）**——用最小成本證明想法可行（紙上原型、一個章節、一場 Boss 戰）
2. **技術驗證**——確認團隊真的做得出來
3. **市場驗證**——在全力開發前就讓人**付錢**（先募資、預購、付費訂閱）
4. **持續 POC / MVP**——每個階段都驗證，不是開頭驗完就算

## 開發流程：Agile + Spiral

### 里程碑結構

```
Brainstorming → PoC → Whitebox → Gameplay → Vertical Slice → Mass Production → Polish
```

### 關鍵原則

- **Vertical Slice 是關鍵**——**提早**把其中一個段落做到接近出貨品質
  - 這是團隊第一次摸到「完成產品」涉及的所有面向
  - 如果 Vertical Slice 都不好玩／不好用，就是根本性的問題
  - 適合拿去找投資人／發行商、做 Demo、做行銷素材
  - 只有通過 Vertical Slice 的專案，才算真正進入量產

- **同心圓開發**——從設計支柱向外擴張
  - 先做核心系統（每根支柱的最小必要部分）
  - 核心穩了才向外擴
  - 要縮 scope 時，從最外圈往內砍
  - 準備多套不同 scope 的計畫（MVP 思維）

- **時程估算**：至少加 20% buffer 吸收未知；不熟悉的工作 buffer 要更多
- **Wishlist**：放不進 scope 的想法進 Wishlist，時間有剩再做
- **Polish 階段**：預留總開發時間的 20-25%；不加新功能，只修 bug 與打磨

### Pre-Production 文件

1. **遊戲／產品設計文件（GDD）**——願景、支柱、系統、玩法、故事、美術風格
2. **里程碑與工作計畫**——支柱 → 系統 → 任務拆解，排程含 buffer
3. **預算與現金流**——所有支出都記錄原因；每個人都要領到錢（至少基本薪）

## 加速開發

### 會議

- **會前**：明確主題、預估時長、提前通知、只找相關人
- **會中**：說明決策影響、一次一個主題、先釐清目的再討論方法、用視覺化／範例輔助
- **會後**：記錄決策**與原因**、集中管理會議紀錄

### 決策

- **可逆 vs 不可逆**——只有不可逆的決策需要深思
- 可逆決策：快速決、馬上試、從結果學
- 投票流程：列出所有選項 → 討論優缺點 → 不限次數投票 → 從最高票開始試 → 平手時由 Producer 拍板

### 團隊歸屬感

- 給成員 **Sense of Ownership**（不是單純執行別人的 vision）
- 開放討論 + 公平決策流程 → 信任
- 歡迎挑戰、誠實面對問題
- 結果由**團隊層級**共同承擔（不要把失敗歸咎於提案人）
