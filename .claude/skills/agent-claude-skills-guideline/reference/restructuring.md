# Restructuring Checklist——拆／合／改 skill 架構時的閉環檢查

## 執行模式

**這份 checklist 由 AI 自主執行，使用者只看回報、做決策。**

- AI 偵測到使用者在動 skill 架構時，自動讀本檔、把所有檢查項當作 AI 自己的動作清單
- 不要把檢查項當成「請使用者照表跑」——所有 grep、所有跨檔比對、所有同步動作都是 AI 跑
- 跑完用「回報格式」回給使用者：哪些 OK、哪些有漏洞、哪些需要使用者決策

**何時啟用**

- 抽出某段功能成獨立 skill（例：SERP 分析從 seo-article 抽出成 serp-analysis）
- 合併兩個 skill
- 改動接力鏈握手位置（軟接 ↔ 硬接 ↔ 審稿斷點）
- 改動 skill 階段順序或編號
- reference 子檔搬家

純內容改動（改文案、補規則條目、修錯字、bump patch version）不算動架構，不跑本 checklist。

**核心精神**：跨檔引用要連動更新；AI 改完前先 grep、不要只看標題。

---

## 1. AI 動架構前——先 grep 跨檔引用

AI 動架構前先跑三個 grep，把結果列成「要連動更新的引用清單」：

```bash
# 舊 skill 名是否還被引用
grep -rn "{舊 skill 名}" .claude/skills/

# 舊階段編號（若拆出某階段、後續會上移）
grep -rn "階段[一二三四五六七八九]" .claude/skills/{涉及的 skill}/

# 舊 reference 路徑（子檔搬家時）
grep -rn "reference/{舊檔名}" .claude/skills/
```

也 grep daily-todo 中的相關待辦（清單 #7 會用）：

```bash
grep -l "{舊 skill 名 / 舊功能名}" daily-todo/
```

引用清單列完才開始改檔——避免改完才 grep 補洞。

---

## 2. AI 改上游 skill

| AI 檢查項 | AI 動作 |
|:--|:--|
| description | 更新觸發詞、不適用清單（是否要加新的下游 skill）、接力對象描述 |
| body 末段 hard-code invoke | 改 invoke 對象 / 新增 invoke / 刪除已遷走的 invoke |
| 「絕對不要觸發 X」清單 | 新斷點寫進這裡 |
| 階段編號 | 拆出某階段後、後續編號上移；reference 內部引用連動（清單 #4） |
| 輸入要求 | 從哪個 skill 取 context、context 形狀是否變 |
| version bump | patch（修 bug）／minor（加功能）／major（破壞性改動） |

---

## 3. AI 改下游 skill

| AI 檢查項 | AI 動作 |
|:--|:--|
| description | 加「{上游 skill} 完成後會硬接力本 skill」表述、寫清楚是否自動 invoke / 是否問使用者 |
| 啟動檢查 | context 是否齊全的防呆（缺欄位就停下問） |
| 工作流階段 | 新 skill 的階段骨架完整（前置 / 主體 / 驗收 / 輸出） |
| version bump | 同上游 |

---

## 4. AI 改 reference 子檔

| AI 檢查項 | AI 動作 |
|:--|:--|
| 子檔內部階段編號 | grep 抓舊編號（05-11 第一波踩點：`serp-flow.md` 開頭還寫「階段一 SERP 分析執行流程」） |
| 跨檔 link 路徑 | reference 子檔搬家後，所有 `[link](path)` 連動更新 |
| 內部例子／案例 | 是否引用了已遷走的子檔、舊 skill 名 |
| 子檔開頭定位語 | 「本檔是 {skill 名} 的 {功能}」這類定位語連動更新 |

---

## 5. AI 改接力位置——5 構件雙向鎖定

**只有改到接力位置（軟接 ↔ 硬接 ↔ 斷點、新增 / 移除接力）才跑這節。** 純內容改動跳過。

| 構件 | AI 要寫到哪 |
|:--|:--|
| 1. 上游 body hard-code invoke 指令 | 上游 SKILL.md 末尾獨立段落 |
| 2. 問 OK／不問 OK 的明確規則 | 同段落 |
| 3. 不要觸發的例外清單 | 同段落 |
| 4. 接力時傳遞具體 context（路徑、參數、必要 metadata） | 同段落 |
| 5. 下游鏡像對應 ＋ 雙向鎖定 | 下游 description ＋ 上游「絕對不要」清單 |

**雙向鎖定的精神**：AI 要在兩端都寫，不是只在上游寫一句 invoke 就完事。硬接 / 軟接的差別只在構件 2，判斷依據是「鏈條中間有沒有人類要審視的決策點」——有就是斷點、沒有就硬接。

---

## 6. AI 同步 memory

| AI 檢查項 | AI 動作 |
|:--|:--|
| feedback memory | 新增（全新規則）／升級（既有規則擴大覆蓋——例：單條斷點升級為完整 5 段鏈規則） |
| MEMORY.md 索引 | 新 memory 加一行索引；改名連動更新；刪除移除索引行 |
| 既有 memory 是否過期 | 架構改動讓舊 memory 矛盾時，當下更新或刪除 |

---

## 7. AI 同步 daily-todo

**踩點預防**：AI 刪除舊待辦前必 grep 確認新 skill 真有對應內容、不是只看標題（05-11 第二波踩點：把「keyword research 方法說明」誤標成「serp-analysis 已涵蓋」並刪除，但 serp-analysis 只把主關鍵字當必填輸入、完全沒涵蓋「怎麼挑、怎麼查」）。

| AI 檢查項 | AI 動作 |
|:--|:--|
| 相關待辦標完成 | grep 新 skill 內容、確認真有對應、不是只看標題 |
| 滾入後續清單 | 動架構過程新發現的優化點、未驗證的設計 |
| 遺留日期標籤 | 純機械性的 (MM-DD) 標籤直接補（依 memory 規則） |

---

## 8. AI 驗證

| AI 驗證項 | 工作時間不夠時 |
|:--|:--|
| 整鏈跑一次（手感驗硬接 / context 傳遞 / 抗誤觸發） | 主動建議使用者滾入後續、註明何時驗證 |
| 獨立呼叫跑一次（若新 skill 支援獨立呼叫） | 同上 |
| 既有測試案例不退回（既有文章 / 既有報告） | 同上 |

依 memory 規則「skill 改完沒驗證時 AI 主動提醒或滾入後續待辦」——AI 驗證做不到當下，主動建議使用者滾入後續或下次驗證時機，不靜默放著。

---

## AI 跑完的回報格式

跑完 8 節後，AI 用以下結構回報給使用者：

```
動架構檢查回報

✅ 已自動完成：
- {清單項 X：做了什麼}
- {清單項 Y：做了什麼}

⚠️ 發現需要使用者決策：
- {清單項 Z：發現 A 與 B 衝突，要選哪個？}

🚧 滾入後續待辦：
- {驗證項 W：當下工作時間不夠，建議下次接力跑時驗}
```

回報精神：使用者只看三類——AI 做了什麼、AI 卡在哪需要決策、AI 把什麼丟給未來驗證。所有 grep 結果、逐項對照都是 AI 內部跑、不灌進回報。
